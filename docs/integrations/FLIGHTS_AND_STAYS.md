# Flights and Stays: Price Offer Integration Plan

**Reviewed:** October 26, 2026. **Status:** provider research complete; no production provider is approved or connected. This is a technical review, not a substitute for signed partner terms or legal review.

## Decision

Keep live travel offers out of implementation until NomadAI confirms an eligible contracting path, defines its pilot markets, receives partner approval, and samples live production inventory for the chosen search scenarios. Project status confirmed on 2026-10-26: no company legal entity has been established. This does not by itself prove that an individual path is unavailable, but no provider has confirmed an individual applicant would be accepted for NomadAI. The current destination catalogue enables Kyrgyzstan (`KG`) only. The repository does not identify user origin markets, preferred dates/passenger mix, provider accounts, or signed commercial terms, so production eligibility and local demand cannot be confirmed here.

The narrowest practical candidate is **accommodation search for a stay in Bishkek, with search, details, and redirect to Booking.com Demand API**, subject to managed-affiliate approval and a production sample. For flights, **Skyscanner Travel APIs** are a separate candidate, subject to partnership approval and route samples. Booking.com’s [general Demand API page](https://developers.booking.com/demand) marks flights as “coming soon,” while its [current detailed service documentation](https://developers.booking.com/demand/docs/getting-started/overview) lists accommodations, car rentals, attractions, and beta transfers, but no flight service. Do not plan a single Booking.com connection for both domains. These are candidates only, not a provider decision to launch.

## Development data and production offers

Use `OFFERS_DEMO_MODE=true` only with `APP_ENV=development` to exercise the traveler form and result cards. The backend returns local, deterministic fixtures with an explicit development-only warning, illustrative totals, and no supplier URLs. The development form also loads an offline airport reference list generated by `scripts/refresh_airport_reference.py`; the browser makes no request to OurAirports. This mode makes no external calls. It must stay off in test and production deployments; the normal provider path remains disabled until `OFFERS_ENABLED=true` is backed by an approved provider integration.

Open datasets can help with reference fields, but they are not live commercial offers:

- [OurAirports data](https://ourairports.com/data/) is public domain and can support airport names and IATA codes. OurAirports provides no guarantee of accuracy or fitness; the dev form uses it only for text suggestions, not to claim a route is currently served. It does not include current schedules, fares, or seat availability. Refresh the bundled subset manually with `python3 scripts/refresh_airport_reference.py` and review the diff before committing it.
- [OpenStreetMap data](https://www.openstreetmap.org/copyright) can support geography and place-name examples. It is licensed under ODbL and requires attribution; publishing a derived database can also trigger share-alike obligations. It does not provide room rates, accommodation availability, or supplier booking links.

For UI development, the local demo fixtures are the default recommendation: they avoid external rate limits, contract assumptions, and open-database licensing obligations while keeping every result visibly non-bookable. Do not present public reference data as a current flight or hotel offer.

## Proposed sample matrix before any selection

These are test cases to validate with product and provider accounts, not claims about user demand or inventory.

| Search | Proposed inputs | Evidence required |
|---|---|---|
| Stay in Bishkek | Two adults, one room, two nights; one near-term date and one date several months out; display in the user-selected currency if supported. | Production results for multiple properties; total price including mandatory taxes/charges; room count, cancellation and payment terms; current availability recheck; supplier URL retaining partner attribution. |
| Flight to Kyrgyzstan | Select origin airports from product analytics and confirmed target user markets; two adults; one-way and return date windows. | Production results per origin; carrier/stop/fare coverage; total price, currency, baggage and change/refund conditions; booking-agent link; live price recheck behavior and availability gaps. |

Before calling the results comparable, use the same traveler count, dates, currency, stay length, room count, baggage needs, fare type, and mandatory charges. Call a price a discount only when the provider supplies a comparable reference price and terms. Otherwise show the total as returned, source, retrieval time, and any exclusions.

## Read-only MVP and freshness rules

- Keep offers separate from AI itinerary JSON, hotel recommendations, sponsored places, and trip cost estimates. The bundled hotel catalogue is static recommendation data; it is not a current price offer.
- Keep all provider credentials server-side. Never put them in frontend bundles, trip records, logs, or source control.
- Return provider, `fetched_at`, currency, total price, availability state, material fare/room conditions, and supplier handoff URL. Do not call an item current after a provider error or expired result.
- Revalidate availability/price before handoff where the provider supports it. If it cannot be revalidated, tell the traveler the supplier may change price or availability during handoff.
- Do not cache or retain provider payloads until the signed provider terms establish what is allowed and for how long. Keep only the normalized fields and event data permitted by those terms.
- Disabled feature, unsupported market, no results, provider failure, and stale response must each produce an explicit state. Never substitute seeded hotels or model-written prices as live offers.
- MVP handoff stays external. NomadAI does not take payment, issue tickets, confirm hotel bookings, manage cancellations, or promise the cheapest market price.

3. Run the representative sample matrix against each approved sandbox and production account. Keep sandbox and production conclusions separate. Record actual response fields, booking conditions, route/property availability, and failed searches with retrieval timestamps.
4. Product/engineering review that evidence and choose one provider path and market before OFFERS-02. If the contracting entity is ineligible, the provider declines access, or coverage/terms fail the sample, defer the feature and do not build an unconnected mock integration.

**Current decision:** no provider is production-approved; **defer OFFERS-02** until the above gates are met. The Booking.com/Skyscanner options are recommendations for partner applications and evidence gathering, not authorization to enable live offers.

The API currently has a provider-independent search contract guarded by `OFFERS_ENABLED=false`. It returns an explicit unavailable response and makes no provider calls. This disabled boundary is preparatory only: it does not provide offers, select a provider, or change the approval gate above.
