# Chat edit concurrency and retries

Each trip has a chat revision. A continuation reads the revision and itinerary before calling the AI and enrichment providers. Only after that work completes does a conditional update advance the revision and save any changed itinerary. The update matches the original revision and owner; no trip write lock is held across provider calls. Every successful continuation advances the revision, including replies without an itinerary update, so concurrent chats cannot commit against an outdated history. A losing request rolls back both messages and usage, and receives HTTP 409. The traveler must reload the latest trip before retrying the message.

Clients can supply a UUID `request_id` with a chat message. A successful response stores the key and a hash of the submitted content on the assistant message in the same transaction as the itinerary, both messages and usage. Repeating the same key and content returns that assistant message and the current itinerary without calling providers or consuming usage again. Returning the current itinerary avoids replacing newer edits with an old retry result. A key reused with different content receives HTTP 409. Concurrent retries with the same key are reconciled after the revision check. Keys are scoped to a trip and last as long as its message history. Existing clients may omit the key, but cannot safely retry an ambiguous network failure without risking a second edit.

The traveler keeps the same key when retrying an uncertain failure. After an explicit conflict, it reloads and uses a new key for a deliberate retry against the latest state. Ownership is checked before request-key lookup; guest chat remains unavailable. An uncommitted provider failure or conflict consumes no chat usage, while each committed continuation consumes usage once. HTTP 409 does not consume usage.

PostgreSQL tests use independent sessions and controlled provider responses in temporary schemas, including overlapping edits, same-key retries, a conflict retry, and rollback. CI supplies `TEST_POSTGRES_URL`; without it these integration tests are skipped.
